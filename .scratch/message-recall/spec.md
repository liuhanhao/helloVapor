# 消息撤回

Status: resolved（2026-09-01 已交付：01 / 02 / 03 全部 resolved。服务端联调 **196 项**全绿（176 基线 + 20 项撤回用例），前端单测 13 项通过，CDP 冒烟四项全过。证据见 `issues/03` 的 Comments）

## 问题陈述（Problem Statement）

消息发出去就收不回来了：打错字、发错人、发错群，只能再补一条「不好意思上一条发错了」。`message` 表没有任何「这条消息已撤回」的痕迹，客户端也就无从渲染。

本功能是 ROADMAP 的 **B2**。它此前一直停在 `needs-info`，卡在四个会决定数据模型的选择上（撤回时限、删除语义、撤回后未读怎么算、对端怎么感知）——这四个已于 2026-09-01 拍板，见文末「决策记录」。

## 解决方案（Solution）

在 `message` 表加一个可空的 `recalled_at`，撤回即**软删**：消息行留着，但**对外不再返回原文**，代之以提示文案。撤回后经 WS 新增的 `chatMessageRecalled` 帧实时通知对端。

关键的成本事实：因为走软删，**未读计数一行都不用改**——它数的是消息条数，而撤回不改变条数。这也是选软删而非硬删的主要理由（见决策记录第 2 条）。

## 词汇决策（Domain vocabulary）

| 术语 | 含义 | 说明 |
| --- | --- | --- |
| **撤回（Recall）** | 发送者把自己已发出的消息撤回来，对所有人同时生效 | 消息行仍在，但内容不再对外可见 |
| **撤回位点**（不用这个词） | — | 与 `CONTEXT.md` 的「**已读位点**」（我读到哪）方向完全不同，不要类比 |

其余沿用既有词汇：**消息**、**会话**、**群聊**、**成员**、**收件主体**。

**Avoid（避免）：**

- **「删除」指撤回** —— 删除是另一个方向（仅我自己不看），本功能**不做**删除，见「超出范围」
- **「已读回执」** —— 那是「对方看没看我的消息」，与本功能和「已读位点」都不同
- **把撤回叫「撤销」** —— 领域里用「撤回」，与界面文案一致

**`CONTEXT.md` 需新增「撤回（Recall）」词条**（本表即为来源）。

## 用户故事（User Stories）

1. 作为发错消息的用户，我希望把已发出的消息撤回，以便不必再补一条解释
2. 作为收到消息的用户，我希望对方撤回后我这边也变成提示，以便不看到对方不想让我看的内容
3. 作为群成员，我希望群里任何人撤回消息我都能看到提示，以便知道少了一条
4. 作为正在会话中的用户，我希望撤回**立刻**生效，而不是刷新后才看到
5. 作为发送者，我不希望别人能撤回我发的消息
6. 作为撤回者，我希望撤回后未读数按我预期变化（不因撤回而凭空少一条或多一条）
7. 作为已退群的成员，我不希望还能撤回群里的消息

## 实现决策（Implementation Decisions）

### 数据模型

- `message` 表新增可空字段 **`recalled_at`**（`Double`，Unix 秒含小数），与 `created_at` 同一套单位
- 空值 = 未撤回。**不用 Bool**：时间戳能支撑日后「撤回发生在多久之后」这类问题，成本为零
- 迁移 `AddMessageRecalledAt` 可回滚（`revert` 删列）。**SQLite 一次只能加一列**（群聊 01 踩过），本迁移只加一列，但 `prepare` / `revert` 仍各写一条 `.update()`
- 迁移按顺序追加在 `configure.swift` 的 `ReadState.Migration()` 之后
- **原文留在库里，但不对外返回**——撤回是「不再给你看」，不是「从世界上抹掉」

### 协议（沿 ADR-0002「扩展而非重新设计」）

新增一种帧，**沿用 `type` / `data` 外壳，不新增顶层字段**：

```json
{
  "type": "chatMessageRecalled",
  "data": {
    "id": "<消息 id>",
    "recipientType": "user",
    "recipientId": "<用户 id 或群 id>",
    "content": "张三 撤回了一条消息"
  }
}
```

- `recipientType` / `recipientId` 让客户端定位到是哪个会话，与 `chatMessage` 帧的 `data.to.type` / `data.to.userid` 同构
- `data.content` 是**服务端生成**的提示文案。为什么由服务端给：收到这一帧时客户端可能根本没加载这个会话（拿不到发送者昵称），自己拼不出文案
- 扇出范围与发消息时一致：**群聊给除发送者外的每个在线成员，单聊给对端**。发送者自己不回推（它自己发起的，本地已更新）；离线用户静默跳过，不做离线补偿

### 服务端

- **`POST /chat/messages/:id/recall`**，走 `UserToken` 鉴权，未带 token 401
  - 非法 UUID → 400；消息不存在 → 404
  - **只有发送者能撤回**（`mine_userid == myId`），否则 403
  - 收件主体是群时**要求成员身份**（沿用 `GroupMember.requireMembership`），已退群不能再撤，403
  - **幂等**：已撤回过则直接返回当前状态，不重复写库、不重复扇出
  - 成功返回 `{ "id": ..., "recalledAt": <unix秒> }`
- **`GET /chat/history`**：`HistoryMessageDTO` 新增 `recalled: Bool`。已撤回时 **`content` 换成提示文案**（不返回原文），文案按查看者生成：自己发的 → 「你撤回了一条消息」，别人发的 → 「`昵称` 撤回了一条消息」
- **`GET /chat/sessions`**：`SessionLastMessageDTO` 同样新增 `recalled: Bool`，最后一条是已撤回消息时预览显示提示文案
- **未读计数不改**：它数的是消息条数，撤回不改变条数（决策记录第 3 条）。**实施时确认不要在累加循环里把 recalled 的消息排除掉**——那会让角标和「点进去看到的条数」对不上
- `WebSocketService` 需要对外开放一个批量推送的 seam：新增 `broadcast(_ json:to userIds:)`
  （`Task` 里操作 WebSocket 会撞 `NIOLoopBound` 断言——见 ROADMAP「动 WebSocket 相关代码前必读」第 1 条，在接口里复用既有 `send(json:to socket:)` 即可）
- 路由注册在 `routes.swift` 的 `tokenProtected` 分组内

### 前端

- `api.ts` 新增 `recallMessage(token, messageId)`
- `stores/chat.ts` 新增 `recallMessage(recipientId, messageId)`：调用成功后更新本地那条消息（置 `recalled`、换成提示文案）与该会话的预览
- 收到 `chatMessageRecalled` 帧：按 `recipientId` 定位会话，按 `id` 找到消息更新；找不到消息也要更新会话预览（用帧里的 `content`）
- 会话列表预览、历史气泡都**按 `recalled` 换样式**：气泡渲染成居中灰色提示行，不再显示头像与时间
- 撤回入口：自己已发出的消息（`fromSelf && acked && id && !recalled`）在悬停时显示「撤回」。**不做右键菜单、不做二次确认弹窗**（撤回本身是用户主动点的，且不限时、可预期）
- 不引依赖，不新增 SVG

## 测试决策（Testing Decisions）

- 服务端联调 `web/e2e-check.mjs`：**现有 176 项须全绿**（回归基线）。新增用例：
  - 撤回自己的消息成功，返回 `id` 与 `recalledAt`
  - **已撤回消息不泄漏原文**（`content` 不含原文，且 `recalled === true`）——这是撤回的实质，必须有
  - 自己看的提示是「你撤回了一条消息」，对方看的是「`昵称` 撤回了一条消息」
  - 撤回**他人**的消息 403；撤回不存在的消息 404；非法 UUID 400；未带 token 401
  - **撤回后未读数不变**（与撤回前一致）
  - 会话列表预览变成提示文案
  - 群消息撤回成功；**已退群成员撤回群消息 403**
  - 对端收到 `chatMessageRecalled` 帧（`recipientType` / `recipientId` / `content` 齐全）
  - 重复撤回幂等（第二次也 200，且不重复推帧）
- 前端：`npm run build` 与 `npm test` 通过
- 手工冒烟：两连接互发 → 一方撤回 → 另一端气泡与会话预览实时变成提示；刷新后仍是提示

## 超出范围（Out of Scope）

- **删除（仅我删）** —— 与撤回是两个数据模型：撤回改的是消息本身，删除要 per-user 的删除标记，且**未读语义不同**（我删掉的消息不该算我的未读，而已撤回的仍算）。已拆为独立候选 **B10**，本功能不为它铺路
- **撤回时限**（已决策不限时）
- **撤回后编辑 / 重新发送**
- **撤回后的离线推送补偿**（离线成员下次拉取即可看到提示，不额外补偿）
- **撤回群成员消息的管理员能力**（群角色与权限是 C3，且当前没有管理员）
- **撤回媒体消息后清理文件**（文件仍留在 `Public/uploads/`，与 A3 的孤儿文件回收一并处理）

## 补充说明（Further Notes）

- 阻塞：无硬前置（群聊 01~04、未读 01~03、B7 均已 resolved）
- **已知上限（继承 C1 / 未读）**：`GET /chat/sessions` 先全量取回我的消息再内存过滤，撤回不改这一点，但要改就一起改
- 提示文案由服务端生成，是**刻意**的选择：客户端在收到 `chatMessageRecalled` 帧时可能没有发送者上下文，自己拼不出文案；且文案集中一处不会漂移。代价是服务端带上了一点 UI 文案——这与现有错误 `reason` 的做法一致

## 决策记录（2026-09-01 拍板，实施以此为准）

1. **撤回不限时。** 限时撤回就得服务端校时（客户端时间不可信），为此引入的复杂度换不回对等的价值。

2. **软删，不是硬删。** 消息行留着，只是对外不再返回原文。硬删会让已落地的**已读位点指向一条不存在的消息**，而未读数又是在数消息条数——两者会打架。

3. **撤回后未读数不变。** 因为走软删，条数没变，未读数自然不变。这条是第 2 条的直接推论，不是独立决策；**反面是：累加循环里绝不能把已撤回的消息排除掉**，否则「角标 3、点进去只有 2 条」。

4. **新增协议帧实时通知对端，不靠下次拉取。** 撤回后对方界面还显示原文是不可接受的——那等于撤回没生效。代价是要动 `WebSocketService` 的扇出，但那个 seam（`broadcast`）本来就该有。
