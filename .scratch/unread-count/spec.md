# 未读计数

Status: ready-for-agent（决策已敲定并记入 ADR-0003；实施 tickets 见 `issues/`，从 01 开始按阻塞边顺序认领）

## 问题陈述（Problem Statement）

会话列表完全没有未读提示：用户看不出哪些会话有新消息，只能靠预览文字和记忆去猜。`GET /chat/sessions` 返回了最后一条消息与 `fromSelf`，但没有任何「我看没看过」的信息——服务端不记录已读位置，前端也没有任何未读状态（`web/src` 里 `未读 / unread / badge` 零命中）。

群聊规格把「群聊的未读计数」列入 Out of Scope，注明**依赖单聊未读（B1）先落地**。本功能即 B1，是群未读的前置。

## 解决方案（Solution）

在服务端为每个用户在每个**收件主体**下记一个**已读位点**（时间戳），由 `GET /chat/sessions` 顺带算出未读数一并返回。前端渲染角标，打开会话时标记已读。

关键的成本事实：`sessions` 本来就取回了「我参与的全部消息」并在内存里遍历去重，未读计数只需要在**同一个循环**里累加，不增加任何消息查询。真正的新增只有一张位点表、一个标记已读的接口，以及一次位点读取。

## 词汇决策（Domain vocabulary）

| 术语 | 含义 | 说明 |
| --- | --- | --- |
| **已读位点（Read cursor）** | 我在某个收件主体下已读到的位置（时间戳） | 未读数由它推出。位置是「我读到哪」，不是「消息被读过」 |
| **未读数（Unread count）** | 某个收件主体下，我已读位点之后、不是我发出的消息条数 | 派生值，不落库 |

其余沿用既有词汇：**会话**、**单聊**、**群聊**、**成员**、**收件主体**、**联系人**。

**Avoid（避免）：**
- **已读回执** —— 那是「对方看没看我的消息」，与本功能方向相反，混用会让接口语义彻底错位
- 用「红点」「角标」当领域概念 —— 它们是界面元素，领域里只有「已读位点」和「未读数」
- 用「未读」指「别人没读我的消息」

**已写入 `CONTEXT.md`：是**（「已读位点」词条）。

## 用户故事（User Stories）

1. 作为一个已登录用户，我希望会话列表标出哪些会话有未读并显示条数，以便一眼看出该先看哪个
2. 作为一个已登录用户，我希望打开会话后未读清零，以便不重复处理已看过的消息
3. 作为一个正在会话中的用户，我希望该会话新到的消息不算未读，以便不打断当前对话
4. 作为一个群成员，我希望群消息的未读与单聊同样计算，以便不漏掉群里的讨论
5. 作为一个刚入群的成员，我希望入群之前的群消息不计入未读，以便不被看不到的历史刷屏
6. 作为一个已登录用户，我希望自己发出的消息不计入未读
7. 作为一个未读功能上线的老用户，我希望刷新后未读数依然准确，以便不漏掉关掉页面期间到达的消息

## 实现决策（Implementation Decisions）

### 数据模型

- 新增 `read_states` 表：`id`、`user_id`、`recipient_type`（`user` / `group`，复用 `ChatMessage.RecipientType`）、`recipient_id`、`last_read_at`（Unix 秒，含小数部分）
- `(user_id, recipient_type, recipient_id)` 联合唯一
- 键与 `ChatHistoryController.sessions` 内部已有的 `key = "\(kind):\(peerId)"` 同构，两边对齐
- 迁移可回滚（`revert`）

### 协议

- **WS 不改。** `data.to.type` 已能区分单聊 / 群聊，前端据此定位收件主体即可，不新增字段

### 服务端

- `POST /chat/read`：请求体 `{ "recipientId": "<uuid>" }`，返回 `{ "recipientId": ..., "lastReadAt": <unix秒> }`
  - 收件主体的判定沿用 `/chat/history` 的既有做法：先按 `groups` 表查，命中即群（并要求成员身份，非成员 403）；否则按单聊（禁止传自己的 id）
  - upsert：有记录则更新 `last_read_at`，无记录则插入
  - 走 `UserToken` 鉴权，未携带 token 返回 401
- `GET /chat/sessions`：每个条目新增 `unreadCount: Int`
  - **零额外消息查询** —— 在既有的内存遍历里累加，判定顺序：跳过自己发的（`mine.userId == myId`）→ 跳过 `createdAt <= lastReadAt` → 群消息再跳过入群前的（`createdAt < joinedAt`）
  - 位点在遍历前一次查回：`read_states` 按 `user_id` 查全量，建成 `[key: lastReadAt]`
  - 无位点记录时 `lastReadAt = 0`，即该会话可见的全部消息都算未读（决策记录第 2 条）
- 两个接口的路由都注册到 `routes.swift` 的 `tokenProtected` 分组内

### 前端

- 会话列表条目在未读 > 0 时显示角标；数字超过 99 显示「99+」
- 打开会话时调 `POST /chat/read` 清零；会话打开期间该会话收到新消息也标记一次（节流，避免每条消息一个请求）
- 收到**非当前会话**的消息时，本地把该会话未读 +1（不发请求，等下次 `refreshSessions` 与服务端对齐）
- 未读状态**不持久化到 localStorage** —— 服务端是权威来源，刷新即重新拉取。这与登录态的持久化不是一回事，不要照搬
- 角标样式与既有会话列表条目保持一致，不引图标库

## 超出范围（Out of Scope）

- **已读回执**（对方看没看我的消息）
- @提及单独计数（群聊规格已列为 Out of Scope）
- 未读消息的离线推送
- 「标记为未读」的手动操作
- 按消息 id 的精确位点（本期用时间戳）
- 群聊的未读上限策略（200 人群刷屏问题由「99+」兜住，不做折叠或免打扰）

## 决策记录（2026-09-01 敲定，实施以此为准）

1. **采用服务端已读位点，不用前端本地计数。**
   理由与代价见 **ADR-0003**。**本条推翻了 `ROADMAP.md` 中 B1 的既有决策「先做前端本地计数」**——那条决策的唯一前提是「群聊还没落地，未读的语义尚未定型」，群聊现已上线，前提消失。推翻的直接原因不是跨端，而是**准确性**：未读的价值是「告诉我有什么没看」，一个显示 0 却确实有未读的角标比没有角标更糟；而页面关闭期间到达的消息对一个 Web 应用是常态，本地计数必然漏计。

2. **无位点记录时全部算未读（`lastReadAt = 0`）。**
   这是唯一不会漏报的规则，且自愈——点开一次就建立基线。它与已定的「成员能且只能看到入群之后的群消息」语义完全一致：**能看到就等于可能未读**。代价是老账号首次登录会看到大数字，但那是真相；新账号为 0。

3. **群消息计入未读，与单聊同一套规则。**
   位点按收件主体记，群只是另一种收件主体，**排除群反而要多写代码**；入群时间过滤天然生效（入群前的群消息本就不可见）。数字超 99 显示「99+」。
   _注：群聊规格把「群聊的未读计数」列为 Out of Scope 并注明依赖 B1 先落地——B1 即本功能，故此处一并纳入，不再单独立项。_

4. **位点用时间戳，不用消息 id。**
   与既有的 `joinedAt` 过滤、历史分页的 `before` 参数同构，且无需处理「消息被删除后位点指向空」。代价是同一秒内到达的消息边界不精确——对未读计数没有实际影响。

5. **不做「标记为未读」。**
   没有用户故事要求它，且它会让位点的语义从「我读到哪」变成「我认为我读到哪」，自愈性质随之消失。

## 补充说明（Further Notes）

- 阻塞：无硬前置（A1~A4 与群聊 01~04 均已 resolved）
- `CONTEXT.md` 需新增「已读位点」词条（本 spec 的词汇决策表即为来源）
- **已知上限**：`GET /chat/sessions` 是先全量取回我的消息再在内存里过滤（ROADMAP 已记录该上限），未读计数继承同一上限；量上来后两者要一起改成 SQL 侧聚合，不要只改其中一个
- 前端 store 里不要新增 `unread` 的 localStorage 持久化——服务端是权威来源，本地存一份只会引入第二处真相
