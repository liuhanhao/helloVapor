# 消息搜索

Status: ready-for-human（2026-09-01：`01` 已 resolved，`02` 实现与自动化验证均已完成。服务端联调 **214 项**全绿，前端单测 16 项通过，构建通过。**仅剩浏览器冒烟**——Chrome 的 CDP 调试端点失效，且重启浏览器会关掉正在看的标签页，故留给人工，步骤见 `issues/02` 的 Comments）

## 问题陈述（Problem Statement）

会话一多，找一条历史消息只能靠翻页——`GET /chat/history` 只支持按时间向前翻（`before`），没有任何按内容检索的能力。翻到三个月前那条「密码是多少」要翻几十页。

这是 ROADMAP 的 **B8**，此前停在 `needs-triage` 等待定范围。范围已于 2026-09-01 拍定，见文末「决策记录」。

## 解决方案（Solution）

服务端新增 `GET /chat/messages/search?q=`，在**我可见的消息**里按关键词匹配内容；前端在会话列表顶部加搜索框，有关键词时列表切换为消息结果，点结果跳到对应会话。

关键的成本事实：可见性规则必须与 `GET /chat/history` **完全一致**（单聊两个方向、群要求成员身份且只看到入群之后），否则搜索会变成绕过退群/入群时间限制的旁路。这一套判定在 `ChatHistoryController` 里已有现成形状，复用即可。

## 词汇决策（Domain vocabulary）

**不引入新词**，全部沿用 `CONTEXT.md` 的既有词汇：**消息**、**会话**、**群聊**、**成员**、**收件主体**、**撤回**。

**Avoid（避免）：**

- **「查找」「过滤」** —— 「过滤」暗示是在已有列表上做筛选，而本功能是**按内容检索服务端消息**，两者不是一回事（见决策记录第 1 条）
- **「全局搜索」与「会话内搜索」并列** —— 本期只做前者，不要为后者预留开关
- **「历史」指搜索** —— 历史是按时序翻页（`GET /chat/history`），搜索是按内容定位，两条不同的读路径

**`CONTEXT.md` 无需改动。**

## 用户故事（User Stories）

1. 作为用户，我希望按关键词搜到聊天记录，以便不必一页页往前翻
2. 作为用户，我希望搜索结果标明是哪个人/哪个群里说的，以便判断是不是我要找的那条
3. 作为用户，我希望点搜索结果直接跳到那个会话，以便接着看上下文
4. 作为已退群的成员，我不希望搜到退群前的群里消息（退群即失去该群访问权）
5. 作为刚入群的成员，我不希望搜到入群之前的群消息
6. 作为撤回过消息的用户，我不希望被撤回的**原文**能被搜出来

## 实现决策（Implementation Decisions）

### 服务端

- **`GET /chat/messages/search?q=&limit=20&offset=0`**，走 `UserToken` 鉴权，未带 token 401
  - `q` 缺失或空白 → 400；`limit` 1~50（默认 20）；`offset` ≥ 0
  - 返回 `{ messages: [...], hasMore: Bool }`，按时间**倒序**
- **可见性必须与 `/chat/history` 一致**：
  - 单聊：`to_type = user` 且（`mine_userid = 我` 或 `to_id = 我`）——两个方向都算
  - 群聊：`to_type = group` 且 `to_id` 在我加入的群里，且**只搜入群之后的消息**（`createdAt >= joinedAt`）
    —— 入群时间过滤是 SQL 侧的 `>=`，与 `sessions` 里内存过滤的做法不同但语义一致
- **排除已撤回的消息**（`recalled_at IS NULL`）。撤回是软删，库里**仍是原文**，不排除就等于让撤回形同虚设
- **只匹配文本消息**：媒体消息的 `content` 是文件 URL，拿它做 `LIKE` 只会搜出一堆噪音（搜「jpg」命中所有图片）
  - **实现要点**：`mine_msgType` 旧数据为 NULL（按 text 解读），所以**不能**用 `NOT IN ('image','audio','video')` 在 SQL 侧过滤——那会把老的文本消息一起排除。改为取回后在 Swift 侧按 `image/audio/video` 剔除
- **关键词中的 `%` 与 `_` 未做转义**（已知上限，见下）：`LIKE` 会把它俩当通配符，搜「100%」会命中过多结果。不转义的代价远小于为它写裸 SQL；等真有人抱怨再说
- 结果条目带 `recipientType` / `recipientId` / `recipientName`，前端才能「跳到那个会话」并在结果里显示是哪个人/哪个群
  - 收件主体名：群取 `groups` 表，单聊优先取 `users` 表、无注册记录时回退消息里的发送者快照——与 `sessions` 一致
- 放在 `ChatHistoryController` 内：复用现成的 `usersById` / `groupsById` 私有 helper

### 前端

- `api.ts` 新增 `searchMessages(token, keyword, { limit, offset })`
- `stores/chat.ts`：新增 `searchKeyword` / `searchResults` / `searching` / `searchError` 状态与 `searchMessages()` 动作
  - **搜索结果不进 `sessions`**——它是另一份列表，混进去会污染未读与置顶逻辑
- 会话列表顶部加搜索框：有关键词时列表区域渲染搜索结果，清空关键词恢复会话列表
- 点结果：用 `openConversation(recipientId, identity, kind)` 跳到该会话并加载历史
- 样式沿用会话条目的既有风格，不引依赖、不新增 SVG

### 已知上限（本期接受）

- SQLite `LIKE` 全表扫描，消息量大起来会慢；量上来要加 FTS 或换 SQL 侧聚合（与 C1 的 `sessions` 上限一并考虑，不要只改其中一个）
- 关键词里的 `%` / `_` 未转义，按通配符处理
- **不返回上下文**（命中消息前后各几条）——点进会话即可看到，本期不做
- 不做「仅搜索当前会话」模式

## 测试决策（Testing Decisions）

- 服务端联调 `web/e2e-check.mjs`：**现有 196 项须全绿**（回归基线）。新增用例：
  - 按关键词搜到自己的消息、搜到对方发来的消息
  - 搜不到与自己无关的消息（别人的单聊/别的群）
  - **搜不到已撤回消息的原文**（与 B2 的关键交互）
  - 搜不到媒体消息（content 是 URL）
  - 群消息：成员能搜到、非成员搜不到、**入群之前的群消息搜不到**
  - 空 `q` 返回 400；未带 token 401
  - `limit` / `offset` 生效、`hasMore` 正确
  - 结果带 `recipientType` / `recipientId` / `recipientName`，指向正确的会话
- 前端：`npm run build` 与 `npm test` 通过
- 冒烟：浏览器里搜一个关键词，结果出现且点击能跳到对应会话

## 超出范围（Out of Scope）

- **按发送者 / 时间区间 / 消息类型过滤** —— 没有用户故事要求，关键词够了
- **搜索结果返回上下文**（命中前后各几条）
- **仅搜索当前会话**
- **搜索未读数、会话名或联系人昵称** —— 本期只搜消息内容
- **高亮命中片段** —— 结果里整条显示即可
- **FTS / 索引优化** —— 见「已知上限」

## 决策记录（2026-09-01 拍板，实施以此为准）

1. **按内容检索，不做「会话列表过滤框」。** 最初倾向过滤框（成本低得多），但它是错的：`GET /chat/sessions` 每个会话只返回**最后一条**消息，过滤框只能按会话名和那一条预览过滤，**搜不到消息内容**——而「翻页找一条历史消息」正是这个功能要解决的痛点。省这个成本等于把功能本身省掉了。

2. **全局搜索，不做「仅当前会话」。** 会话内搜索在 UI 上等价于翻页，价值低；先做跨会话的。

3. **不返回上下文。** 点结果直接跳到该会话就能看到前后文，为此多一次查询和一套合并逻辑不划算。

4. **媒体消息不匹配。** 内容字段是文件 URL，对它做 LIKE 是纯噪音（搜「mp4」命中所有视频）。结果只含文本消息。

5. **必须排除已撤回的消息。** 撤回是软删，原文仍躺在 `content` 里。不排除的话，B2 刚建的「撤回即不再给你看」会被搜索直接绕过——这不是遗漏，是让另一个功能失效。
