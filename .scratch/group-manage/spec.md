# 群改名与拉人入群的前端入口

Status: resolved（2026-09-01 已交付：01 / 02 两个 tickets 全部 resolved。**服务端零改动**，e2e 176 项仍全绿；CDP 冒烟五项全过，证据见 `issues/02` 的 Comments）

## 问题陈述（Problem Statement）

群建好之后就定型了：`GroupInfoDialog.vue` 只有成员列表和退群，**群名改不了、人加不进来**——想加人只能重新建一个群。

而服务端的两个接口早已实现、已注册在 `tokenProtected` 下，且 176 项联调的第 17 节（群管理）已把它们的全部行为覆盖完毕：

- `PATCH /chat/groups/:id`（`GroupController.update`）：仅创建者可改，非创建者 403，空名 400，空 body 400
- `POST /chat/groups/:id/members`（`addMember`）：任何成员可拉人，已在群内 409，用户不存在 400，非成员 403，超 200 人 400

缺口**只在前端**：`web/src/api.ts` 里没有这两个接口的封装。群聊 02 的规格把「改群名、拉人入群的前端入口」列为「接口已就绪待接」，本功能即补上这一环。

## 解决方案（Solution）

纯前端：补两个 api 封装 + 两个 store 动作，在群信息弹窗里加改名与拉人的入口。

关键的成本事实：**服务端一行都不用改**，不新增迁移、不扩展 WS 协议。因此本次的验证工作不是「写新的服务端用例」，而是「176 项继续全绿」——这本身就是「零后端改动」的证明。

## 词汇决策（Domain vocabulary）

**不引入新词**，全部沿用 `CONTEXT.md` 的既有词汇：**群**、**成员**、**创建者**、**联系人**、**收件主体**。

**Avoid（避免）：**

- **「邀请」「申请」** —— 群聊 02 已定「建群即入群，被拉入无需本人同意」，说「邀请」会暗示存在同意流程
- **「管理员」「群主」** —— 当前权限模型只有「创建者」一个角色，不做管理员。群角色与权限是 C3 的事，本功能不为它铺路
- **「踢人」** —— 服务端 `leaveGroup` 明确只能退自己，系统里**没有**踢人能力，不要在界面上造出一个不存在的概念
- **「拉群」** —— 用「拉人入群」，与既有文案一致

**`CONTEXT.md` 无需改动。**

## 用户故事（User Stories）

1. 作为群创建者，我希望改群名，以便群名能跟着讨论主题变
2. 作为群成员，我希望把新同事拉进群，以便不必为此重新建群
3. 作为非创建者，我不希望看到改群名入口，以便不点进去才被告知没有权限
4. 作为群成员，我希望拉人时看不到已在群里的人，以便不撞上「该用户已在群内」
5. 作为群成员，我希望拉人失败时看到**具体原因**（已在群内 / 人数已满 / ID 不存在），而不是一句「操作失败」
6. 作为刚被拉进群的人，我希望下次打开时能看到这个群

## 实现决策（Implementation Decisions）

### 接口

- `PATCH /chat/groups/:id`，body `{ name }`。仅创建者可改，非创建者服务端已返回 403。返回 `GroupSummaryDTO`
- `POST /chat/groups/:id/members`，body `{ userId }`。任何成员可拉人
- **注意形状不对称**：`addMember` 只收**单个** `userId`（`AddMemberPayload`），而建群的 `createGroup` 收 `memberIds` **数组**。一次拉多人要前端循环调用，且要处理「中途某个失败」的部分成功
- 本期**只做改名，不做群头像**：`update` 已支持 `avatar` 字段，但头像上传能力在 B3

### 前端

- `api.ts` 新增 `updateGroup(token, groupId, { name })` 与 `addGroupMember(token, groupId, userId)`
- `stores/chat.ts` 新增 `renameGroup(groupId, name)` 与 `addGroupMember(groupId, userId)`，成功后**同步三处状态**：`groups[id]`、`sessions` 里该群条目的 `peer.nickname` / `memberCount`、`recipientNames[id]`
- 成员数**以服务端返回的 `GroupSummaryDTO.memberCount` 为准**，不要本地 `+1`
- 改群名入口：仅 `groups[id].ownerId === auth.user.id` 时渲染
- 拉人：复用 `CreateGroupDialog.vue` 的选人范式（`searchUser` + 结果列表 + 选中），用已加载的成员列表把「已在群内」的人标注出来并禁选
- 错误文案：直接显示 `ApiError.message`——服务端 `reason` 已是可读中文且说明了「为什么」，不要覆盖成笼统的「操作失败」
- 样式沿用群信息弹窗与建群弹窗的既有风格，不引依赖、不新增 SVG

### 已知上限（本期接受）

- **拉人与改名都没有实时通知**。WS 协议不新增帧（沿用 ADR-0002 的克制），其他成员要等下次 `loadGroups()`（刷新页面或重连）才看到新群名/新群，被拉的人同理。代价是新成员可能以为拉人失败了——**缓解：拉人成功后在弹窗里明确提示「对方下次打开时才会看到这个群」**，不要静默成功
- 一次只能拉一个人（服务端接口是单值），批量拉人靠前端循环

## 测试决策（Testing Decisions）

- **服务端零改动**，所以 `npm run e2e` 的 **176 项必须仍然全绿**（这是回归基线，也是「零后端改动」的证明）
- 服务端用例已在第 17 节覆盖：任何成员可拉人 / 重复拉人 409 / 不存在的用户 400 / 非成员 403 / 非创建者改名 403 / 创建者改名与改头像 200 / 空名 400 / 空 body 400。**不需要新增服务端用例**
- 前端：`npm run build`（含 `vue-tsc --noEmit`）通过
- 手工冒烟：创建者改名后会话列表群名同步 / 非创建者看不到改名入口 / 拉人后成员数 +1 且成员列表出现新人 / 拉已在群内的人显示「该用户已在群内」/ 退群后重新被拉入仍从入群时间点起可见

## 超出范围（Out of Scope）

- **群头像上传与修改**（依赖 B3 的头像上传能力）
- **踢人**（服务端 `leaveGroup` 只支持退自己，没有踢人能力）
- **群主转让 / 管理员 / 禁言 / 群公告 / 解散**（C3；且「无主群归谁」未定）
- **拉人需对方同意**（沿用群聊 02 已定的「建群即入群」）
- **实时通知被拉入的人**（WS 不新增帧）
- **批量拉人**（服务端接口是单值）

## 补充说明（Further Notes）

- 阻塞：无硬前置（群聊 01~04 与未读 01~03 均已 resolved）
- **与 B3 的关系**：B3 落地头像上传后，群头像可直接复用本期加的 `updateGroup`（`avatar` 字段服务端已支持），不必再动接口层
- **与 C3 的关系**：本功能**刻意不引入「角色」概念**——创建者判定直接比 `ownerId`。等 C3 真要做管理员时再引入角色，届时这里的判定要一并改，别提前抽象
