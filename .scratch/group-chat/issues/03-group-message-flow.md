# 03 — 群消息端到端流转

**要构建的内容：** 让一条群消息真正跑起来——发出、入库、扇出给所有在线成员、能被历史查回来、出现在会话列表里。这是群聊的曳光弹：竖着切一条完整链路，而不是横着铺开所有功能。

**被阻塞于（Blocked by）：** 01 — 群聊数据模型与迁移；02 — 建群与成员管理接口

**状态（Status）：** resolved

- [x] WS 协议扩展：`data.to` 增加 `type`（`user` / `group`）；群聊时 `to.userid` 位置填群 id
- [x] 服务端校验发送者是该群成员，非成员发消息被拒
- [x] 入库：`to_type = 'group'`、`to_id = 群 id`
- [x] 扇出推送：给该群所有**在线成员**各发一份（发送者自己不回推，仍由 ack 确认）
- [x] 发送者身份继续以连接绑定的身份为准（批次一 A1 已建立），群聊不新开伪造面
- [x] `GET /chat/history`：`peer` 参数泛化为收件主体（用户 id 或群 id）；非成员查群历史被拒
- [x] `GET /chat/sessions`：群会话与单聊会话一起返回，条目带形态标记（`kind: direct | group`）、群名、成员数，仍按最后消息时间倒序
- [x] 群消息未携带 `msgType` 时仍按 `text` 处理
- [x] 三个连接同群互发的端到端联调用例；非成员收不到；单聊行为不变；既有联调全绿

## 实施要点

- **扇出是最容易出问题的地方**：现在是「一条消息 → 一个接收者」，群聊是「一条消息 → N 个在线连接」。注意群规模上限 200（决策记录第 2 条）。
- 推送前同样要用连接绑定的身份覆盖 `data.mine` 的四个身份字段——批次一 A1 里正是因为最初漏了这一步，冒用的身份照样能显示给接收方（推送原本转发的是客户端原文）。
- 群聊气泡需要显示发送者昵称（单聊不需要），接收方靠 `data.mine` 里的 `nickname` 渲染，所以推送内容里这个字段必须是服务端的真实值。
- 会话列表现在是按「对方用户」聚合的（`ChatHistoryController.sessions`），群聊要一并纳入排序，注意别把单聊的聚合逻辑改坏——那是 02 号 issue 的核心能力，回归用例要覆盖。
- 退群的访问语义（决策记录第 4 条）：非成员查历史直接拒绝，不要返回空数组糊弄过去。

实现落点与给后续 issue 的约定：

- **WS 协议只加一个字段**：`data.to.type`（`user` / `group`），缺省按 `user`——iOS 旧格式消息不带该字段，行为完全不变。群聊时 `to.userid` 位置填群 id，不新增字段。服务端推送时会用自己判定的值回写 `to.type` / `to.userid`，客户端原文里的 `to` 不参与路由。
- **被拒的群消息走新的 `chatMessageError` 帧**（`{type: "chatMessageError", data: {reason: "..."}}`）：WS 没有请求-响应，不回帧的话客户端无从知道消息没发出去。`04` 前端要处理这个类型（至少给出提示），否则用户会以为发成功了。
- **成员校验与扇出合成一次查询**：`GroupMember` 按 `group_id` 查全量，一次拿到「发送者是否成员」+「扇出名单」。群不存在与不是成员在这里等价（都查不到成员记录），错误文案合并为「群不存在或您不是该群成员，消息未发送」。
- **`GroupMember` 新增两个静态查询**（`requireMembership` / `counts`），`GroupController` 里原有的私有 `requireMembership`、`memberCounts` 已删除并改为调用它们——`03` 有三个地方（WS、查历史、会话列表）要回答「我是不是这个群的成员」，各自重复查一遍既冗余又容易漏。
- **`GET /chat/sessions` 的 `peer` 语义泛化了**：单聊仍是对方用户，群聊是群（`peer.nickname` = 群名、`peer.avatar` = 群头像、`peer.username` 为空串）。新增 `kind`（`direct` / `group`）与 `memberCount`（仅群条目有值，单聊条目该字段直接不出现在 JSON 里——Swift 的 `encodeIfPresent` 会省略 nil）。**`04` 前端必须先按 `kind` 分支再读 `peer`**，否则群条目会显示成空昵称的用户。
- **`GET /chat/history` 的 `peer` 不需要额外传 kind**：服务端先按 UUID 查 `groups` 表，命中就按群处理（并要求成员身份），否则按单聊处理。群 id 与用户 id 同为 UUID，靠查表区分，前端传 `peer` 即可。
- **`HistoryMessageDTO` 新增 `senderUserId` / `senderNickname` / `senderAvatar`**：群聊气泡要显示发送者昵称，历史消息没有这三个字段就无法渲染（单聊不需要，但一并返回，前端不用分支取数）。
- **入群时间过滤已一并实现**（决策记录第 4 条后半句「重新加入也只能看到加入之后的消息」）。原本打算单独立 ticket，实际成本比预估低，且此时 `04` 前端尚未开工，改语义零返工：
  - `GET /chat/history`：`GroupMember.requireMembership` 返回成员记录，用它的 `joinedAt` 加一条 `created_at >= ?` 过滤。
  - `GET /chat/sessions`：函数开头本来就要查「我加入的群」，顺手把 `joinedAt` 建成 `[群 id: 入群时间]`，在按收件主体去重的循环里跳过入群之前的群消息——**不加这条，会话列表会预览一条点进去读不到的消息**，所以两处必须一起改。
  - 两条路径共用同一语义：**成员能且只能看到入群之后的群消息**。没有入群后消息的群，历史为空数组、不出现在会话列表。
  - 已知上限：`sessions` 是先全量取回我的消息再在内存里过滤（这是它原有的做法，单聊那套聚合逻辑本来就是内存去重），群消息量涨上来之后要改成 SQL 侧按群带 `joined_at` 条件。真到那时再说，本期数据量毫无压力。
