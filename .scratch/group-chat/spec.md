# 群聊

Status: ready-for-agent（决策已敲定，见文末「决策记录」；实施 tickets 见 `issues/`，从 01 开始按阻塞边顺序认领）

## 问题陈述（Problem Statement）

系统目前只能一对一聊天：数据模型里一条消息固定是「一个发送者 + 一个接收者」（`ChatMessage.to` 是单个用户），会话列表按「联系人（对方用户）」聚合，联系人关系由历史消息推导。用户无法把三个人以上拉进同一个对话。`ChatMessage.type` 字段虽然预留了 `single/group/system` 枚举，但只是字符串、从未被读写——群聊能力实际上完全不存在。

## 解决方案（Solution）

引入**群**这一新实体，并把「会话」从「两个人的关系」泛化为「消息收发的上下文」，使其支持两种形态：单聊与群聊。单聊行为完全不变（既有数据与 iOS 协议兼容不受影响）；群聊消息由服务端扇出给所有在线成员，离线成员靠历史查询补回。

## 词汇决策（Domain vocabulary — 已确认）

现有 `CONTEXT.md` 把「会话」定义为「两个用户之间的单聊对话」。群聊一旦进来，这个词会被两种含义撕扯，必须在动工前定死。已定如下，并**已写入 `CONTEXT.md`**：

| 术语 | 含义 | 说明 |
| --- | --- | --- |
| **群（Group）** | 一个持久实体：有名称、头像、创建者、成员列表 | 群本身**不是**会话；它是会话的参与方容器 |
| **会话（Session）** | 消息收发的上下文，有两种形态：**单聊**（两个用户）与 **群聊**（一个群 + 其成员） | 现有定义收窄为「单聊」，不再独占「会话」这个词 |
| **单聊（direct session）** | 两个用户之间的一对一会话 | 需要区分时才用，平时可直接说「会话」 |
| **成员（Member）** | 群内的用户，显式记录的关系 | **不复用「联系人」**——联系人是「由历史消息推导出的对方用户」，成员是显式关系，两者来源不同 |
| **收件主体（recipient）** | 消息投递的目标，取值为「某个用户」或「某个群」 | `ChatMessage.to` 需要泛化成的东西 |

**Avoid（避免）：** 聊天室、频道、channel、圈子、讨论组；用「联系人」指群成员；用「会话」单独指单聊。

**为什么不直接给 `to` 加一个「群 id」字段了事**：那样能跑通，但会让「会话」这个词在代码和文档里同时表示两件事，从此每个读代码的人都要靠上下文猜。先定词，再改模型，改动更小而不是更大。

## 用户故事（User Stories）

1. 作为一个已登录用户，我希望创建一个群并拉入若干用户，以便和多人同时对话
2. 作为一个群成员，我希望在群里发的消息被其他在线成员实时收到，以便进行群聊
3. 作为一个群成员，我希望离线期间错过的群消息在下次打开时能从历史里补回，以便不丢消息
4. 作为一个群成员，我希望群聊气泡上显示发送者昵称，以便知道是谁说的（单聊不需要）
5. 作为一个已登录用户，我希望在会话列表里区分单聊与群聊条目（名称、头像、成员数），以便快速辨认
6. 作为一个群成员，我希望看到群成员列表，以便知道群里都有谁
7. 作为一个群成员，我希望可以主动退群，以便退出不想再参与的群
8. 作为一个已登录用户，我希望未加入的群的消息不会推给我，以便不被无关消息打扰
9. 作为一个单聊用户（既有能力不受破坏），我希望我和别人的一对一聊天行为完全不变，以便本次改动不回退已有功能

## 实现决策（Implementation Decisions）

### 数据模型

- 新增 `groups` 表：`id`、`name`、`avatar`、`owner_id`（创建者）、`created_at`
- 新增 `group_members` 表：`group_id`、`user_id`、`joined_at`，联合唯一；成员关系是**显式记录**的，不能像联系人那样靠消息推导（否则无法区分「已退群」与「还没说过话」）
- `message` 表把收件方泛化为收件主体：新增 `to_type`（`user` / `group`）与 `to_id`，迁移时旧数据按 `user` 回填（旧 `to_userid`）
- `type` 字段（`single/group/system`）当前只是字符串且无人读写；建议废弃，改由 `to_type` 推导，避免同一事实两处记录。是否直接删除需决策

### 协议（遵循 ADR-0002：扩展现有协议而非重新设计）

- WS payload 的 `data.to` 增加 `type`（`user` / `group`），群聊时 `userid` 位置填群 id
- 服务端收到群消息后入库，再扇出给该群所有在线成员（发送者自己不回推，仍由 ack 确认）
- 发送者身份继续以连接绑定的身份为准（issue 01 已建立），群聊不新开伪造面
- 未携带 `msgType` 的消息仍按 `text` 处理

### 服务端

- `POST /chat/groups` 建群（含初始成员）
- `GET /chat/groups` 我加入的群列表
- `GET /chat/groups/:id/members` 群成员
- `POST /chat/groups/:id/members` 拉人入群
- `DELETE /chat/groups/:id/members/:userId` 退群 / 移出成员
- 会话列表接口：单聊与群聊条目统一返回，条目上带形态标记（`kind: direct | group`），仍按最后消息时间倒序
- 历史消息接口：`peer` 参数泛化为收件主体（用户 id 或群 id），语义不变
- 全部接口继续走 `UserToken` 鉴权；WS 连接鉴权已在批次一建立（握手校验 token，身份由服务端解析）

### 前端

- 会话列表条目区分单聊 / 群聊（群条目显示群名与成员数）
- 群聊窗口：气泡显示发送者昵称；输入区与媒体能力复用现有实现
- 建群入口（选择若干用户 → 建群）、群信息页（成员列表、退群）

## 决策记录（2026-08-31 敲定，实施以此为准）

1. **被拉入群不需要本人同意——建群即入群。**
   邀请确认要额外一张 `group_invites` 表 + 待确认状态机 + 前端确认界面，成本高；而且本系统根本没有好友关系（联系人由历史消息推导），缺乏「同意」的社交基础。被拉进不想进的群，用退群解决即可（退群能力在本期范围内）。**不为没发生的问题买单。**

2. **群规模上限 200 人。**
   扇出是在线成员逐个推送，规模直接决定一条消息的写放大倍数。200 足够覆盖真实使用场景，又不会让扇出成为瓶颈。建群与加人时都校验，超限返回明确错误。

3. **群名可改，且只有创建者能改（`PATCH /chat/groups/:id`）。**
   群名不可改会让用户建群时不敢下手（默认名只能叫「群聊(3)」这类）。只允许创建者改，是为了不引入管理员/权限体系——那是一整套模型，本期不碰。

   由此确定本期完整权限规则（实施以此为准）：**任何成员都可以拉人入群；只有创建者能改群名；只能退自己，不能踢别人。** 不做管理员、不做群主转让、不做禁言。

4. **退群即失去该群的访问权：退群后查不到这个群的任何历史，重新加入也只能看到加入之后的消息；群内不发系统提示消息。**
   「不是成员就看不到」是唯一自洽的规则，实现上也最简单（非成员查历史直接拒绝）。重新加入能看到退群前的历史，需要额外记录成员的有效时间段，收益不抵成本。系统提示消息（「XX 已退群」）需要新的消息渲染类型，同样超出本期。

5. **`message.type` 字段保留，但新代码不再依赖它。**
   这个字段现在实际存的是 WS 消息的 `type` 值（`"chatMessage"`），从来没被用来区分单聊/群聊——也就是说它已经被误用了。删除要写迁移、动旧数据；保留零成本。权威来源改为 `to_type`，`type` 字段继续按现状写入以兼容旧数据与外部系统，但任何新逻辑都不读它。

6. **复用现有 `message` 表，加 `to_type` + `to_id`，不分表。**
   分表会让「会话列表按最后消息时间倒序」变成跨表聚合查询，复杂度陡增；MVP 的数据量下单表毫无压力。真到了要分表的时候，说明量已经上来了，那时再评估。**不为假想的性能问题提前设计。**
