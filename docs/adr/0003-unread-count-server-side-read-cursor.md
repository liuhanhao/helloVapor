# 未读计数采用服务端已读位点而非前端本地计数

未读数以服务端记录的**已读位点**为准：每个用户在每个收件主体（单聊的对方用户 / 群）下有一个 `last_read_at`，未读数由服务端在 `GET /chat/sessions` 里算出并返回。刻意不在前端本地累加计数。

**本决策推翻了 `ROADMAP.md` 中 B1 的既有决策「先做前端本地计数」。** 那条决策的唯一理由是「群聊还没落地，未读的语义尚未定型——现在把已读位点做进服务端，等于给一个还没定型的语义提前建模」。群聊已交付并上线，该前提消失，故重新权衡。

推翻的直接原因不是跨端，而是**准确性**：未读的价值是「告诉我有什么没看」，一个显示 0 却确实有未读消息的角标，比没有角标更糟——用户发现一次就不再信任它。纯前端计数只能统计「页面存活期间实时收到的消息」，而页面关闭期间到达的消息（对一个 Web 应用是常态，不是边界情况）会被漏计，刷新后角标显示 0 而会话列表却有新消息预览。

选服务端位点的另一个原因是成本比直觉低：`GET /chat/sessions` 本来就取回了「我参与的全部消息」并在内存里遍历去重，未读计数只需要在同一个循环里累加，**不增加任何消息查询**；真正的新增只有一张位点表、一个标记已读的接口，以及一次位点读取。

代价是引入了一张需要写入的表（标记已读是写操作，且会话列表的每个条目都要读位点），并继承了 `sessions` 已有的量级上限（全量取回消息后在内存过滤）——群消息量涨上来后两者要一起改成 SQL 侧聚合。「跨端同步」这个收益目前兑现不了（iOS 客户端尚未联网，见 B0），但它不是本决策的主要理由。

## Considered Options

- 前端本地计数（内存 + localStorage 持久化）：零后端改动，但页面关闭期间到达的消息漏计，角标会显示 0 而实际有未读
- 前端本地计数 + 红点兜底（无精确数字时只显示红点不显示数字）：不会骗人，但主交互形态退化成红点，拿不到用户想要的条数
- 服务端已读位点（本决策）：计数始终准确且可跨端，代价是一张表和一个写接口
